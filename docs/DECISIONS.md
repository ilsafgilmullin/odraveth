# ODRAVETH — Журнал решений

Технические решения и их обоснования. Продуктовые решения принимает только пользователь; они фиксируются в [`PRODUCT_BASELINE.md`](PRODUCT_BASELINE.md), а здесь — запись об изменении.

Формат: **ID · статус · дата** — контекст, решение, последствия. Статусы: *принято* (техническое решение, можно пересмотреть отдельной задачей с новой записью), *утверждено пользователем* (продуктовое), *временно* (действует до отдельной задачи), *заменено* (пересмотрено более поздней записью).

### D-001 · утверждено пользователем · 2026-10-05 — Движок и язык

Godot Engine **4.7.2 stable**, **GDScript**. C# не используется, 4.8 dev/beta не используется. `config/features` в `project.godot` — `"4.7"`. Скрипт проверок отказывается работать с другой версией.

### D-002 · принято · 2026-10-05 — Рендерер Compatibility

**Контекст:** 2D карточная игра, Android — платформа №1, важен охват устройств.
**Решение:** `gl_compatibility` (OpenGL ES 3.0) для десктопа и мобильных.
**Почему:** максимальная совместимость с Android-устройствами, включая те, где Vulkan отсутствует или работает нестабильно; возможностей 2D-рендеринга достаточно для UI карточной игры.
**Последствия:** часть продвинутых эффектов Forward+/Mobile недоступна. Переход на `mobile` — одна настройка, но требует проверки на устройствах.

### D-003 · утверждено пользователем / принято · 2026-10-05 — Экран и ориентация

- Утверждено: 1920×1080, stretch `canvas_items`, aspect `expand`, только альбомная ориентация.
- Принято: ориентация `sensor_landscape` (альбомная в обе стороны, без портретной) — телефон можно держать любой стороной.
- Принято: на десктопе окно 1280×720 (`window_*_override`) — только для удобства разработки, на Android не влияет.

### D-004 · принято · 2026-10-05 — Набор autoload

**Решение:** autoload только `EventBus`, `SceneRouter`, `AppState`, `CardDatabase`. `SaveManager` — обычный класс, экземпляром владеет `AppState`.
**Почему:** каждый autoload обязан быть глобальным (сигнальная шина; роутер, переживающий смену сцен; состояние приложения; неизменяемые справочные данные). `SaveManager` — ввод-вывод без связи с деревом сцен: как класс он тестируется с временным путём и не даёт произвольным скриптам писать сохранение в обход `AppState`.
**Последствия:** обоснование и запись здесь — обязательное условие для нового autoload.

### D-005 · принято · 2026-10-05 — Навигация через SceneRouter и параметры маршрутов

**Решение:** все переходы — через `SceneRouter` по id из `Routes`; данные между экранами — параметрами маршрута (`apply_route_params`), а не через глобальные синглтоны. История — стек `{route, params}`; режимы push / replace / reset.
**Почему:** требование ТЗ не хранить runtime-состояние матча в глобальных структурах; единая точка для истории и кнопки «Назад» Android; экраны не знают путей к сценам друг друга.

### D-006 · принято · 2026-10-05 — Формат сохранений

**Решение:** локальный JSON в `user://odraveth_save.json`, обязательное поле `save_version` (сейчас 1), атомарная запись (`*.tmp` + rename), пошаговые миграции `_migrate_from_vN`, защита от перезаписи сохранения более новой версии, копия повреждённого файла.
**Почему:** JSON читаем человеком и безопасен (в отличие от `str_to_var`/`bytes_to_var` с объектами); `save_version` — требование ТЗ; атомарность защищает от порчи при закрытии приложения Android во время записи.
**Последствия:** числа в JSON — `float`, код чтения приводит типы явно.

### D-007 · заменено D-017 · 2026-10-05 — Формат данных карт (предварительный)

**Решение:** предварительно — JSON в `res://data/cards/`, файл `{"cards": [...]}`. Проверяются только утверждённые инварианты (раздел 8 ARCHITECTURE).
**Почему:** структура `data/` из ТЗ предполагает файлы данных; JSON удобно ревьюить в diff и валидировать.
**Последствия:** окончательная схема и типизированная модель карты подтверждаются в Stage 1; формат может измениться.

### D-008 · принято · 2026-10-05 — Строки интерфейса

**Решение:** русские строки пишутся прямо в сценах и скриптах; файлов перевода нет.
**Почему:** первая версия только на русском. Godot умеет извлекать строки из сцен/скриптов в POT, если локализация понадобится позже.
**Последствия:** идентификаторы и комментарии в коде — на английском, документация — на русском.

### D-010 · принято · 2026-10-05 — Системная кнопка «Назад» Android

**Решение:** `quit_on_go_back=false`; `SceneRouter` обрабатывает `NOTIFICATION_WM_GO_BACK_REQUEST` отложенно: есть история — назад, корневой экран — выход из приложения.
**Почему:** по умолчанию Godot закрывает приложение на любом экране. Отложенный вызов обязателен: смена сцены во время рассылки уведомления вызывает ошибку движка (найдено smoke-тестом).
**Последствия:** подтверждение выхода из идущего боя — задача экрана боя.

### D-011 · принято · 2026-10-05 — Тесты без сторонних фреймворков

**Решение:** собственный headless smoke-тест (`tests/smoke_test.tscn`) и `tests/run_tests.sh`; GUT/gdUnit4 не подключаются.
**Почему:** ТЗ запрещает сторонние зависимости без необходимости; для Stage 0 достаточно одной сцены-теста. Тест перехватывает ошибки движка через `Logger` (доступен в 4.7), поэтому скрытые ошибки не проходят незамеченными.
**Последствия:** при росте числа тестов (MatchEngine) можно вернуться к вопросу фреймворка отдельным решением.

### D-017 · принято · 2026-10-06 — Схема карт, формат JSON и данные эффектов

**Контекст:** Stage 1 превращает каркас CardDatabase в строгую типизированную базу 40 утверждённых карт. Эффекты на этом этапе не исполняются. Заменяет D-007.
**Решение:**
- JSON в `res://data/cards/` — канонический источник: пять файлов по фракциям (`ashravael.json`, `nerqathen.json`, `dumoryss.json`, `khevaruun.json`, `neutral.json`), каждый — `{"cards": [...]}`.
- Поля карты: `id`, `name_en`, `name_ru`, `faction`, `type`, `rarity`, `cost`, `deck_limit`, `rules_text_ru`, `effects`; у существ — `attack`, `health`, `armor`; у артефактов с зарядами — `charges`. Неизвестные поля запрещены.
- Конвейер: JSON → `CardSchema.validate()` → `CardSchema.build()` → `CardDefinition` (типизированные `Faction.Id`, `CardEnums.Type`, `CardEnums.Rarity`) → `CardDatabase`. Загрузка «всё или ничего»; наружу отдаются только копии.
- Эффекты — декларативные `CardEffectSpec`: `effect_id`, необязательный `keyword`, `trigger`, `conditions`, `actions`, `limits`. Идентификаторы — из закрытого словаря `EffectVocabulary`. Каждый идентификатор используется хотя бы одной утверждённой картой.
- Недоопределённое в текстах не дописывается: срок без указания в тексте — `NOT_STATED` (Q-17); у Натиска, Провокации и Предсмертия есть только метки (Q-18). Оба вопроса закрыты в ТЗ Stage 2 (D-020).
- Ничего не исправляется молча: некорректная карта проваливает загрузку целиком.
**Почему:** JSON удобно ревьюить в diff и проверять строго; модель без исполнения позволяет зафиксировать данные, не придумывая механику до решения открытых вопросов; закрытый словарь не даёт данным разойтись с будущим MatchEngine.
**Последствия:** MatchEngine будет исполнять `CardEffectSpec`; расширение словаря — только вместе с утверждённой картой и тестом. Тип `CURSE` поддерживается схемой, но словарь пока не содержит триггеров для проклятий: они появятся вместе с утверждёнными картами-проклятиями.

### D-018 · утверждено пользователем · 2026-10-06 — Осколки души, закрытие Q-12

**Контекст:** Q-12 («Осколки души: на что тратятся, есть ли предел») был открыт с Stage 0.
**Решение (прямое решение пользователя в ТЗ Stage 1):** Осколок души — ресурс Неркатена, не карта и не энергия. Старт 0, максимум 10; сохраняется между ходами; не бывает отрицательным; избыток при получении теряется (9 + 2 = 10); тратится только эффектами, где расход прямо указан; эффект с обязательной стоимостью больше текущего запаса активировать нельзя. Способность Вхоразеля «Извлечение» не меняется.
**Реализация на Stage 1:** только данные — `GameRules.STARTING_SOUL_SHARDS = 0`, `GameRules.MAX_SOUL_SHARDS = 10`, действия `GAIN_SOUL_SHARDS` / `SPEND_SOUL_SHARDS`, условия и множитель для карт Неркатена. Счётчика во время матча, менеджера ресурса и состояния в `AppState` нет; runtime-логика Вхоразеля не реализуется.
**Последствия:** PRODUCT_BASELINE §5.3; Q-12 удалён из открытых вопросов.

### D-021 · принято · 2026-10-06 — Устройство MatchEngine

**Контекст:** нужен детерминированный, полностью тестируемый движок матча без God-object, состояние — отдельно от правил.
**Решение:**
- `MatchEngine` (`scripts/battle/match_engine.gd`) — обычный `RefCounted`, **не autoload**: один экземпляр — один матч, им владеет тот, кто проводит матч (позже — экран боя). Карты получает через инжектируемый источник с `get_card(id)` (`CardDatabase`), случайность — через инжектируемый `MatchRng`.
- Состояние — только данные: `MatchState`, `PlayerState`, `CardInstance` (карта в колоде, руке, сбросе), `CreatureInstance` (существо на поле), `ArtifactInstance`. `CardDefinition` общий и неизменяемый; всё изменяемое — в экземплярах.
- Правила — статические модули без собственного состояния: `CommandValidator` (проверка и список допустимых команд), `TurnFlow` (подготовка, замена, ход), `CardPlay`, `Combat`, `HeroPowers`, `CostCalculator`, `TargetRules`, `TriggerDispatcher`, `EffectExecutor`, `EffectConditions`. Общие изменения состояния (урон, добор, гибель, броня, Осколки, артефакты) — в `MatchResolver`, единственном объекте с указателем на состояние и RNG. Модули получают его параметром, поэтому циклических ссылок `RefCounted` (и утечек) нет.
- Эффекты исполняются по данным `CardEffectSpec`; 40 карт в коде движка не дублируются. Поддерживаются только идентификаторы `EffectVocabulary`, которые используют утверждённые карты; неизвестное действие — ошибка движка.
- Команды — `MatchCommand` (сериализуются в словарь для повторов), результат — `ActionResult` с кодом ошибки, событиями и признаком ожидаемого выбора. Журнал — структурированные события `MatchEvent` (id и данные, без строк для показа).
**Почему:** состояние легко клонировать и сравнивать снимками; правила тестируются по отдельности; UI и ИИ получают проверку и список допустимых команд из одного места.
**Последствия:** ARCHITECTURE §9. Новый autoload не добавлялся; состояние матча не хранится ни в `AppState`, ни в другом autoload.

### D-022 · принято · 2026-10-06 — Поле `timing` в данных эффектов

**Контекст:** ТЗ Stage 2 (§20) различает «когда» (WHEN) и «после того как» (AFTER). В данных Stage 1 момент не был записан: формулировка была только в `rules_text_ru`.
**Решение:** у эффекта появилось поле `timing` из закрытого словаря `EffectVocabulary.TIMINGS` = `WHEN` / `AFTER`. Оно обязательно для событийных триггеров и запрещено для `ON_PLAY`, `ENTER_BATTLE`, `LAST_BREATH`, `STATIC`: их момент задают сами правила. Значения проставлены по тексту карт: «после», «после того как» → `AFTER` (02, 03, 05, 11, 21, 37); «когда» → `WHEN` (08, 16, 17, 19, 26, 29). У «Пустостекла» (24) и «Сердца бастиона» (32) в тексте нет ни одной из формулировок. Их эффекты относятся к самому моменту оплаты и розыгрыша, поэтому — `WHEN`.
**Почему:** момент срабатывания — данные карты, а не код движка; схема по-прежнему ничего не дописывает молча.
**Последствия:** 14 эффектов получили поле `timing`; характеристики, стоимости и тексты карт не менялись. Схема проверяет поле (3 новые негативные фикстуры). Независимая таблица ожидаемых значений — `tests/card_database_tests.gd` (`EXPECTED_TIMINGS`).

### D-023 · принято · 2026-10-06 — Порядок разрешения

**Решение:**
- Каждое атомарное изменение (урон, добор, изменение характеристик, призыв…) завершается шагом `MatchResolver.step()`: гибель существ → пересчёт статических способностей → проверка исхода → разрешение очереди WHEN.
- WHEN-срабатывания разрешаются сразу после шага, который их вызвал, но не повторно-входно: срабатывания, вызванные разрешением WHEN-эффекта, ждут его окончания в той же очереди. AFTER-срабатывания копятся в отдельной очереди и разрешаются `drain()` после завершения команды или срабатывания и его непосредственных последствий. Обе очереди — явные массивы в `MatchState` (FIFO).
- Порядок слушателей одного события: существа на поле слева направо, затем артефакт. Одновременные гибели: поле активного игрока слева направо, затем поле противника; для каждого погибшего сначала «Предсмертие», затем «гибель союзного существа» (PRODUCT_BASELINE §5.10).
- Исход проверяется после каждого шага. Как только здоровье героя ≤ 0, матч заканчивается; очереди, отложенные действия и ожидаемый выбор очищаются, и ничего больше не разрешается. Отсюда и правила «Кровавого приказа», «Клеймённого кровью», «Кровавой десятины» и «Жатвы душ».
- Розыгрыш карты (`CardPlay`): цена (энергия, расход модификаторов стоимости, способности фазы стоимости противника) → карта покидает руку → WHEN «противник платит увеличенную стоимость» / «противник разыгрывает карту» → существо выходит на поле, «союзное существо разыграно», «Вход в бой» / заклинание исполняется и уходит в сброс / артефакт заменяет активный → AFTER.
- Атака (`Combat`): урон обеим сторонам считается до нанесения и наносится в одном шаге; затем «пережило атаку» (AFTER) и «после атаки» (AFTER).
- Конец хода: отложенный урон («Клятва пепла») → разрешение очередей → истечение временных эффектов, Эхо и Отложения → неизрасходованная энергия обнуляется → пересчёт статических способностей → ход противника.
**Почему:** явные очереди исключают неконтролируемую рекурсию; порядок полностью определён.

### D-024 · принято · 2026-10-06 — Детерминизм, RNG и снимки

**Решение:**
- `MatchRng` — абстракция: `next_int(n)`, `shuffle(array)` (Фишер–Йетс через `next_int`), `get_state()` / `set_state()`. Реальный матч — `DeterministicRng(seed)` с собственным `RandomNumberGenerator`; тесты — `ScriptedRng` (заданная последовательность). Глобальные `randi()` / `randf()` / `randomize()` в коде матча запрещены; тест проверяет это поиском по исходникам `scripts/battle`.
- Порядок обращений к RNG фиксирован: первый игрок (`next_int(2)`) → перемешивание колоды игрока 0 → колоды игрока 1 → после замены стартовых карт перемешивание колоды каждого заменявшего (сначала первый игрок) → случайные цели эффектов («Печать горнила») по мере разрешения.
- Замена стартовых карт: решения обоих игроков записываются и разрешаются вместе, когда решили оба; поэтому порядок подачи решений не влияет на результат.
- `snapshot()` — канонические простые данные (ход, игроки, руки, порядок колод, поле, характеристики, статусы, артефакты, сброс, сгоревшие карты, очереди, исход) плюс состояние RNG; изменение снимка не меняет матч. События нумеруются (`seq`) и хранят номер хода.
**Последствия:** один seed и одни команды дают идентичные снимки после каждой команды и идентичный журнал (replay-тест).

### D-025 · принято · 2026-10-06 — Транзакционность команд и предохранители

**Решение:**
- Команда сначала полностью проверяется `CommandValidator` без изменения состояния; отвергнутая команда возвращает код ошибки и ничего не меняет.
- Принятая команда выполняется целиком. Предохранитель: не больше `MatchResolver.MAX_RESOLUTIONS_PER_COMMAND = 500` разрешений срабатываний за команду. При превышении (или неподдерживаемом действии) команда откатывается: состояние восстанавливается из клона, сделанного до команды (без копирования журнала, журнал усекается), RNG — из сохранённого состояния; возвращается `ENGINE_ERROR`.
- Ссылки на объекты в очередях хранятся как id; источник срабатывания ищется заново при разрешении, поэтому погибшее существо не разрешается повторно и не умирает дважды.
**Почему:** ТЗ §11, §25, §33: никаких частичных изменений, никакого зависания.

### D-026 · принято · 2026-10-06 — Цели и выбор игрока

**Решение:**
- У карты не больше одной выбранной цели; её используют все ссылки `CHOSEN_*` эффектов розыгрыша.
- Заклинание с выбранной целью («Клятва пепла», «Жатва душ», «Расколотый миг», «Обряд закалки», «Железная память») и способности Кежарина и Тажириона без валидной цели использовать нельзя (`TARGET_REQUIRED`).
- Существо, чей «Вход в бой» требует цели, при наличии валидной цели обязано её получить; если валидной цели нет, существо разыгрывается, а часть способности с целью ничего не делает. Остальные действия выполняются: например, «Клеймённый кровью» всё равно наносит 1 урон своему герою.
- «Второе погребение» требует свободного места на поле и погибшего союзного существа в сбросе, иначе розыгрыш отвергается. «Последнее погибшее» — последняя карта существа, попавшая в сброс владельца и ещё лежащая там.
- Выбор количества Осколков «Скупщика душ» — обязательный параметр команды (`soul_shards_to_spend`, 0…min(3, Осколки)); движок его не подставляет.
- «Тренический картограф»: если в колоде ≥ 2 карт, матч ждёт отдельной команды `CHOOSE` от владельца. Выбранная карта остаётся сверху, вторая уходит под низ колоды; затем разрешение продолжается. Пока выбор не сделан, другие команды отвергаются (`CHOICE_PENDING`).
**Почему:** правила целей нужны и UI, и ИИ; `get_legal_commands()` перечисляет все допустимые варианты, включая цели и выбор.

**Superseded:** пункт выше, разрешавший существу с обязательной целью «Входа в бой» разыгрываться при отсутствии валидной цели, отменён явным пользовательским решением D-031. Остальная часть D-026 сохраняется как история решения.

### D-027 · принято · 2026-10-06 — Стоимость карт

**Решение:** `CostCalculator.quote()` считает текущую стоимость, ничего не меняя.
1. Базовая стоимость (у Эхо — его собственная базовая).
2. Ожидающие увеличения «следующей карты» от противника, от старых к новым. Каждое проверяет стоимость **на этот момент** (`only_cost_at_most`). Заряд «Искажения» — не больше одного на карту, следующий ждёт следующей подходящей карты. Остальные увеличения («Шрам разума», «Дань Завесе») складываются; `cost_cap` («Дань Завесе», 10) ограничивает результат.
3. Способности фазы стоимости противника («Пустостекло») — против получившейся стоимости, с учётом `per_turn` и условий.

Модификаторы расходуются и заряды тратятся только при фактическом розыгрыше. Цена, показанная для карты в руке, совпадает с ценой оплаты; карта, ставшая слишком дорогой, отвергается, и заряд остаётся. «Увеличено вами» — итоговая стоимость минус базовая (все увеличения в игре исходят от противника).

**Подтверждение:** порядок и семантика стоимости явно утверждены пользователем повторно в D-032; D-032 уточняет stacking «Шрама разума» и максимум одно «Искажение» на разыгрываемую карту.

### D-028 · принято · 2026-10-06 — Детали хода, статусов и отдельных карт

**Решение:**
- Обязательный добор в начале хода выполняется в **каждом** ходу, включая первый ход первого игрока: в ТЗ Stage 2 (§11) исключения нет.
- В конце хода `energy_current` обнуляется (временная энергия «Осколка импульса» исчезает; в начале следующего своего хода энергия всё равно восстанавливается).
- «За ход» — за каждый ход, чей бы он ни был: счётчики `per_turn`, атаки, флаги «герой получил урон в этом ходу» и «союзное существо погибло в этом ходу» сбрасываются в начале каждого хода у обеих сторон.
- Статические способности («пока…», «если…»: «Орриксийский путник», «Реликвеносец Келварна», Натиск «Изверга войны») пересчитываются с нуля после каждого шага и не накапливаются. Появление статической брони: +N к максимальной и текущей; исчезновение: −N к максимальной, текущая не выше новой максимальной.
- «Отложение»: флаг ожидания; в начале следующего хода владельца существо блокируется на этот ход, в конце этого хода статус снимается. Повторное наложение до отработки ничего не продлевает.
- «Эхо»: новая карта из **базового** определения заклинания, стоимость `max(1, базовая)`, срок — конец следующего хода владельца «Пиявки эха». Разыгранное Эхо не уходит в сброс; сгоревшее при полной руке — в зону сгоревших карт.
- «до конца вашего следующего хода» («Разрушитель Завесы») — до конца следующего хода владельца эффекта; `NOT_STATED` и `PERMANENT` — постоянно, пока экземпляр на поле.
- «Второе погребение»: создаётся **новый** экземпляр существа (новый id) из базового определения: здоровье = 1, максимальное здоровье и броня — базовые; ничего от погибшего экземпляра не переносится; «Вход в бой» не срабатывает.
- «Печать горнила» без союзных существ: действия выполняются в порядке данных — заряд расходуется, усиливать некого (ТЗ Stage 2: следовать порядку действий).
- «Клятва пепла»: урон в конце хода записывается как отложенное действие с id цели; если цели нет на поле, урона нет.
- «Обряд закалки»: счётчик полученной от этой карты брони хранится в экземпляре существа (`armor_gained_from`), потеря брони его не сбрасывает.

### D-031 · принято · 2026-10-06 — Обязательные CHOSEN_* цели без обхода для существ

**Источник:** явная пользовательская corrective-правка Stage 2.

**Решение:**
- Любая карта с обязательной выбранной целью `CHOSEN_*` может быть разыграна только при наличии валидной цели и с явно переданным валидным `target_id`; тип карты значения не имеет.
- Старое исключение из D-026 для существ с targeted «Входом в бой» отменено. Отдельного creature bypass нет.
- «Клеймённый кровью» при отсутствии вражеского существа и «Призыватель лат» при отсутствии другого союзного существа отвергаются до мутации. «Призыватель лат» не может выбрать самого себя.
- `CommandValidator` является авторитетной pre-mutation проверкой; `get_legal_commands()` не содержит невозможный `PLAY_CARD`, а `get_valid_play_targets(...)` возвращает пустой список при отсутствии обязательной цели.
- Отвергнутая команда сохраняет снимок состояния, RNG и журнал событий без изменений.

**Почему:** обязательность цели — часть допустимости команды, а не опциональная часть эффекта после выхода существа на поле.

### D-032 · принято · 2026-10-06 — FIFO и stacking модификаторов стоимости

**Источник:** явное пользовательское утверждение corrective-аудита Stage 2.

**Решение:**
- Все ожидающие cost modifiers обрабатываются FIFO по времени создания. Каждый проверяет своё условие на текущей running cost после всех более старых применившихся модификаторов.
- Не прошедший условие модификатор пропускается без расходования и остаётся pending.
- «Шрамы разума» складываются на одной карте, пока каждый следующий проходит условие ≤ 3: 2 → 3 → 4 расходует два; 3 → 4 оставляет второй pending.
- Одновременно может храниться несколько зарядов «Искажения», но на одну разыгрываемую карту применяется максимум один. Остальные заряды остаются pending.
- «Дань Завесе» находится в той же FIFO-очереди и сохраняет свой локальный cap 10; новый глобальный cap не вводится.
- Текущий `CostCalculator` уже реализует эту семантику; production-код стоимости не переписывается без необходимости, семантика закрепляется regression-тестами.

**Почему:** порядок создания должен быть наблюдаемым и детерминированным, а условные заряды не должны исчезать на неподходящих картах.
