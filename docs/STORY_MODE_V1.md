# Story Mode V1 — «Страница без имени → Испытание Цитадели» (Stage C)

Статус: реализовано 2026-10-11 в `claude/story-mode-v1-citadel` от `develop`
`29e3d856b2f15825d5e60e3e067f930e3ffd0f1d`. Решение: D-065.

Первый полный сюжетный цикл: пролог → сюжетное вступление в Цитадели → подготовка
героя и колоды → сюжетный бой по обычным правилам → результат → сюжетное
последствие реального исхода. Обычный режим «Войти в Нулмерис» не изменился.

## 1. Пользовательский путь

```
Главное меню → История (Библиотека) → «ХРОНИКИ» → «ПРОЧИТАТЬ ПРОЛОГ»
  → пролог, 3 страницы → «ВОЙТИ В ЦИТАДЕЛЬ»
  → «ИСПЫТАНИЕ ЦИТАДЕЛИ»: вступление, 3 страницы → «К ПОДГОТОВКЕ»
  → подготовка: герой · колода · испытание → «НАЧАТЬ ИСПЫТАНИЕ»
  → Prebattle (STORY) → «НАЙТИ СОПЕРНИКА» → Opponent Search → Battle (Mulligan …)
  → Result (STORY) → «ПРОДОЛЖИТЬ ИСТОРИЮ» → последствие
  → «ПОВТОРИТЬ ИСПЫТАНИЕ» | «В ХРОНИКИ» | «ГЛАВНОЕ МЕНЮ»
```

Отдельной кнопки, позволяющей пропустить пролог и сразу начать бой, нет.
Дополнительная кнопка «НАЧАТЬ СЮЖЕТ» в «Хрониках» не добавлена: она вела бы на ту же
первую страницу пролога, что и сохранённая «ПРОЧИТАТЬ ПРОЛОГ», и только дублировала
бы действие.

## 2. Разделение Normal / Story

| | Обычный режим | Сюжетный режим |
|---|---|---|
| Вход | «Войти в Нулмерис» | «Хроники» → пролог |
| Prebattle | без изменений | подпись «СЮЖЕТНЫЙ БОЙ · ЦИТАДЕЛЬ», «МОДИФИКАТОРЫ: НЕТ» |
| Соперник | `OpponentSelector.pick_with_seed` (зеркало ~10 %) | `OpponentSelector.pick_story_trial_with_seed` |
| `BattleLaunchConfig.mode` | `NORMAL` (по умолчанию) | `STORY` + chapter + return route |
| Result | ПОВТОРИТЬ БОЙ · НОВЫЙ СОПЕРНИК · СМЕНИТЬ КОЛОДУ · ГЛАВНОЕ МЕНЮ | ПРОДОЛЖИТЬ ИСТОРИЮ · ПОВТОРИТЬ ИСПЫТАНИЕ · В ХРОНИКИ · ГЛАВНОЕ МЕНЮ |
| Back на Result | Главное меню | «Хроники» |

Признак режима не хранится в autoload или глобальной переменной: Prebattle получает
его параметром маршрута `story_chapter` (`StoryFlow.PARAM_CHAPTER`), дальше он
путешествует только внутри `BattleLaunchConfig`. Неизвестный chapter id
игнорируется, и экран работает как обычный.

## 3. Сюжетные страницы

Пролог (`StoryPrologueScreen`) сохранён без изменений текста; изменилось только
финальное действие: «ВОЙТИ В ЦИТАДЕЛЬ» всегда открывает `Routes.STORY_CITADEL`.

Вступление «ИСПЫТАНИЕ ЦИТАДЕЛИ» (`StoryCitadelScreen.PAGES`) — утверждённые тексты:

1. **ХРАНИТЕЛЬ** — жезл, кольца Цитадели, «первое испытание нынешней
   Конвергенции»; акцент «Для героев оно действительно первое.»
2. **ЧЕТЫРЕ СЛЕДА** — четыре следа победы, каждый записан так, будто остальные трое
   проиграли; акцент «Все четыре записи подлинны.»
3. **ПРОТИВОРЕЧИЕ** — неизвестно, какая победа была первой; стёртые строки прежних
   циклов; акцент «Войди в испытание и сохрани то, что Книга снова попытается забыть.»

Имя «Одравет» на сюжетных экранах не появляется (проверяется тестом).

## 4. Подготовка

Вид `PREPARATION` того же экрана показывает три панели:

- **ГЕРОЙ** — production-портрет, имя, фракция; «СМЕНИТЬ ГЕРОЯ» или «ВЫБРАТЬ ГЕРОЯ»;
- **КОЛОДА** — название, `30/30` и маркер «ГОТОВА» либо «НЕТ ГОТОВОЙ КОЛОДЫ»;
  «СМЕНИТЬ КОЛОДУ» или «СОБРАТЬ КОЛОДУ»;
- **ИСПЫТАНИЕ** — «СЮЖЕТНЫЙ БОЙ · ЦИТАДЕЛЬ», «МОДИФИКАТОРЫ: НЕТ», соперник — один из
  трёх других героев, бой идёт по обычным правилам.

Строка готовности текстом (не только цветом) объясняет, чего не хватает.
«НАЧАТЬ ИСПЫТАНИЕ» доступна только при выбранном герое и готовой выбранной колоде
(`PlayerSetupData.selected_deck`, то есть `DeckValidator`). Hero Select и Deck Builder
открываются существующими экранами через `SceneRouter.go_to()`; после возврата экран
заново читает `AppState.profile`. Колода игроку автоматически не создаётся.

Переход «вступление → подготовка» выполняется `replace_with(STORY_CITADEL,
{view: "preparation"})`, чтобы запись истории маршрутов указывала на подготовку и
Back из Hero Select / Deck Builder / Story Prebattle возвращал именно туда.

## 5. Выбор сюжетного соперника

`OpponentSelector.story_trial_weights()` / `pick_story_trial()` /
`pick_story_trial_with_seed()` — отдельные методы; обычные `weights()` и `pick()`
не изменены.

- допустимы только три других стартовых героя, точное зеркало запрещено;
- веса равные целочисленные (по 1), порядок канонический (`PlayerSetupData.HERO_IDS`);
- выбор использует отдельный setup-`DeterministicRng` с новым seed
  (`BattleLaunchConfig.generate_seed()`), это не RNG матча;
- соперник фиксируется в конфигурации до анимации Opponent Search;
- колода ИИ — существующая техническая генерация `technical_opponent_deck()`, без
  нового имени.

## 6. BattleLaunchConfig metadata

| Поле | Тип | NORMAL | STORY |
|---|---|---|---|
| `mode` | `BattleLaunchConfig.Mode` | `NORMAL` | `STORY` |
| `story_chapter` | `StringName` | `&""` | `STORY_CHAPTER_CITADEL_TRIAL` (`&"citadel_trial"`) |
| `story_return_route` | `StringName` | `&""` | `Routes.HISTORY` |

`set_story(chapter, return_route)` принимает только id из `STORY_CHAPTERS`.
`rematch()` и `with_opponent()` копируют метаданные (`_copy_metadata`). Opponent
Search, Battle и Result передают тот же объект конфигурации. `BattleSession` читает
только героев, колоды, сложность и seed: метаданные не попадают в MatchEngine, RNG,
AI, карты, урон, стоимость, порядок хода или исход. Тест сравнивает NORMAL и STORY с
одинаковыми входами: снимки движка и исход совпадают.

## 7. Маршрутизация исхода

- Result в STORY показывает тот же авторитетный исход и статистику движка, но
  действия: **ПРОДОЛЖИТЬ ИСТОРИЮ** (основная), **ПОВТОРИТЬ ИСПЫТАНИЕ**,
  **В ХРОНИКИ**, **ГЛАВНОЕ МЕНЮ**; над заголовком — «ИСПЫТАНИЕ ЦИТАДЕЛИ».
- «ПРОДОЛЖИТЬ ИСТОРИЮ» → `Routes.STORY_AFTERMATH` с исходом и конфигурацией.
- «ПОВТОРИТЬ ИСПЫТАНИЕ» (Result и последствие) → `config.rematch()`: тот же герой,
  точный снимок колоды, тот же соперник и сложность, STORY-контекст, новый seed.

Последствие (`StoryAftermathScreen`, тексты в `StoryFlow`):

| Исход | Заголовок | Текст |
|---|---|---|
| Победа | КНИГА ПРИНЯЛА ПОБЕДУ | «Книга записывает победу {игрок}. … в этом же испытании победил {соперник}. Обе записи подлинны.» |
| Поражение | СТЁРТЫЙ ОТТИСК | «Книга записывает победу {соперник}. … {игрок} уже выходил из этого испытания победителем.» |
| Ничья | РАЗДЕЛЁННАЯ СТРАНИЦА | «Книга делит страницу надвое. В одной строке пал {игрок}, в другой — {соперник}. …» |

Общая строка: «Хранитель закрывает страницу раньше, чем герои успевают её прочесть.»
Имена — реальные герои игрока и соперника; для корректной русской речи `StoryFlow`
склоняет имена в родительном падеже и согласует глагол с родом героя (Сирравет —
женский род: «победила», «пала», «выходила … победительницей»). Смысл утверждённых
текстов не меняется. Без корректной STORY-конфигурации экран показывает безопасную
запись «ЗАПИСЬ НЕДОСТУПНА» с «В ХРОНИКИ» и «ГЛАВНОЕ МЕНЮ».

## 8. Модификаторы, прогресс, награды

- «МОДИФИКАТОРЫ: НЕТ» показывается в подготовке и в Story Prebattle; payload
  модификаторов отсутствует (тест проверяет поля конфигурации).
- Нет сохранения сюжетного прогресса, флагов прохождения, открытия глав, наград,
  опыта, валюты, рейтинга и достижений. Глава повторяема; поражение и ничья —
  полноценные исходы.
- Save schema (`CURRENT_SAVE_VERSION = 2`) и поля профиля не меняются; тест проходит
  цикл дважды и сравнивает профиль и файл сохранения.
- «Прогресс» скрыт; Q-15 открыт.

## 9. Back contract

| Экран | Back |
|---|---|
| Пролог, страница > 1 | предыдущая страница |
| Пролог, страница 1 | Библиотека на «ХРОНИКИ» (`StoryFlow.open_chronicles`, история сбрасывается) |
| Вступление, страница > 1 | предыдущая страница |
| Вступление, страница 1 | последняя страница пролога (`replace_with`) |
| Подготовка | последняя страница вступления |
| Hero Select / Deck Builder из подготовки | подготовка |
| Story Prebattle | подготовка (без истории — `reset_to` подготовки) |
| Opponent Search | Story Prebattle (без истории — Story Prebattle с параметром главы) |
| Battle | прежнее подтверждение выхода |
| Story Result | «ХРОНИКИ», не обычный режим |
| Последствие | «ХРОНИКИ» |

Сюжетные экраны используют `replace_with` и `reset_to`, поэтому повторные циклы
не наращивают историю: во время боя стек ограничен записями «Главное меню →
Библиотека → подготовка → Story Prebattle», повтор боя её не удлиняет, а возврат в
«Хроники» очищает её. `HistoryShell.apply_route_params` принимает `section`
только из списка `SECTIONS`; иное значение игнорируется.

## 10. Тесты

`tests/story_mode_v1_tests.gd` (модуль `story_mode`, 180 проверок; входит в
`tests/smoke_test.gd` и `tests/visual_alpha_smoke.tscn`):

- контракты конфигурации, выбора соперника (никогда не зеркало, все три достижимы,
  равномерность 30 000 жребиев) и неизменный обычный mirror-контракт;
- утверждённые страницы, отсутствие имени Одравета и developer-слов;
- блокировка без героя/колоды, возврат из Hero Select и Deck Builder;
- Normal/Story separation на Prebattle, конфигурации и Result;
- E2E по реальному MatchEngine: Story Prebattle → Search → Battle → настоящая
  партия до конца → Result → последствие нужного исхода → rematch с новым seed;
- победа / поражение / ничья открывают соответствующие последствия;
- одинаковые входы NORMAL и STORY дают одинаковые снимки движка и исход;
- цепочка Android Back, ограниченная история маршрутов;
- повторное прохождение без дублирования узлов и сигналов и без записи профиля;
- containment, touch targets ≥ 64 px и помещение текста на 1600×900, 1920×1080,
  2400×1080, 2800×1752.

`tests/story_prologue_tests.gd` обновлён под новое финальное действие пролога
(Испытание Цитадели вместо прямого перехода в Hero Select / Deck Builder /
Prebattle). Мутационные проверки (зеркало в сюжетном жребии, потеря метаданных в
`rematch()`, панель шире экрана) валят соответствующие проверки.

Visual QA: сценарии `story-citadel-intro`, `story-citadel-no_hero`,
`story-citadel-ready`, `story-prebattle`, `story-result-{victory,defeat,draw}`,
`story-aftermath-{victory,defeat,draw}` рендерятся на четырёх разрешениях.

## 11. Ограничения

- Реальное Android-устройство не проверялось (только headless/Xvfb рендер).
- Сюжетная глава одна; следующая глава, модификаторы (этап L1+) и «Прогресс»
  требуют отдельных решений.
- Колода ИИ остаётся технической генерацией.
- Склонение имён и согласование рода заданы таблицей для четырёх стартовых героев;
  для будущих героев требуется дополнить `StoryFlow._GRAMMAR` (иначе используется
  именительный падеж и мужской род).
